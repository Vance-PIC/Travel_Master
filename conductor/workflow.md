# Workflow Protocol: 旅行大師文件治理機制 (Doc-Gov x Git-Flow)

本文件定義本專案的「唯一合法工作流程」。在執行任何文件產出前，必須嚴格遵守此順序。

## 第一層：宏觀治理階段 (Macro Phases D1~D5)
這是專案整體的生命週期。

| 階段 | 名稱 | 執行動作與目標 |
| :--- | :--- | :--- |
| **D1** | **資料輸入與背景對齊** | 用戶提供參考資料/筆記。AI 釐清專案目標、對象、與核心限制條件。 |
| **D2** | **建立規格與範本** | AI 分析資料，產生專屬的「文件架構藍圖」與「空白標準範本」。 |
| **D3** | **物理拆分與建檔** | 依照範本架構，將原始資料切割為多個獨立的 `.md` 檔案，準備並行撰寫。 |
| **D4** | **微觀章節撰寫循環** | **核心工程期。針對 D3 產生的檔案，逐一執行「第二層：八步協作流程」。** |
| **D5** | **合併與發布驗收** | 待所有章節完工，物理合併為一份完整手冊。執行最後的全域校閱與版號晉升。 |

---

## 第二層：微觀八步協作流程 (Micro Steps 1~8)
此為 **D4 階段** 內，針對「單一 `.md` 檔案」必須嚴格執行的迭代迴圈。未完成 Step 8 前，禁止進入下一份檔案。

| 步驟 | 動作 | AI 的責任 | 用戶的責任 |
| :--- | :--- | :--- | :--- |
| **Step 1** | **討論 (Discuss)** | 執行 `audit-chapter.ps1`，列出該檔案的「紅燈缺口」。提出修補策略。 | 針對缺口提供意見或新資訊。 |
| **Step 2** | **修改 (Modify)** | 根據討論，產出該段落的「具體修改草案」。 | 確認草案方向。 |
| **Step 3** | **共識 (Consensus)** | 明確詢問「是否同意上述修改草案？」 | 回覆「同意/PASS」或要求退回重擬。 |
| **Step 4** | **產出 (Track)** | 僅輸出**被異動區塊**的 Markdown 原始碼（先印後改）。 | 核對原始碼。 |
| **Step 5** | **合併 (Master)** | 在背景物理寫入/覆蓋至 `src/` 對應的檔案中。 | - |
| **Step 6** | **檢視 (Review)** | 再次執行審計確保轉綠燈。列出本次變更對整體的「連動影響（如預算/時間）」。 | 做最後檢查。 |
| **Step 7** | **定版 (Finalize)** | 在看板上將該檔案標記為 `[READY]`。 | 給予最終定版指令。 |
| **Step 8** | **切換 (Switch)** | 宣布本章節循環結束，自動引導進入「下一份檔案」的 Step 1。 | - |

---
**【最高鐵律】**：
- 在未完成上述流程圖的制定與雙方共識前，AI 絕對禁止擅自進入實作。
