# Spec：旅程規劃 P1–P3 航班決策與訂票比價

- 狀態：待使用者審閱
- 日期：2026-10-27
- 原型：`scratch/ui-preview/trip-planner-v4.html`
- 範圍：從保留旅遊選項，到追蹤候選航班，再比較訂票通路價格

## 1. 目標

讓使用者在地點與日期尚未完全確定時先建立草案，透過價格追蹤比較航班，再以指定旅客組成查詢選定航班的訂票通路與整組總價。使用者最後能從通路連結前往訂票。

成功時，使用者能清楚分辨：

- P1 航班搜尋與加入候選
- P2 候選航班的單人票價趨勢與決選
- P3 依成人數、兒童數與兒童年齡取得通路報價和訂票入口

## 2. 已確認的產品規則

1. P1 草案保留出發地、可選目的地、去程日期範圍、回程日期範圍及旅客組成。
2. 成人與兒童分開設定；每位兒童需輸入出發日年齡。旅客組成須沿流程帶到 P3。
3. P1 搜尋結果顯示符合草案條件的航班。使用者按「加入候選」後，系統同時開始該航班組合的價格追蹤。
4. 候選組合以目的地、去程日期與班號、回程日期與班號識別。日期與班號都必須納入身分，避免不同日期的同班號被合併。
5. 移除候選會一併停止其價格追蹤。單獨停止追蹤則保留候選，之後可恢復追蹤。
6. P2 每組追蹤航班有自己的頁籤；切換頁籤檢視該組價格趨勢與目標價。走勢以單人來回票價比較。
7. 使用者在 P2 選定一組航班後進入 P3。P3 顯示該組已選航班，不再要求使用者重新選一次。
8. P3 依 P1 的成人數、兒童數及每位兒童年齡查詢各訂票通路。價格比較以整組旅客總價為主，並提供成人與每位兒童的票價明細。
9. 使用者從 P3 的通路連結前往完成訂票。本產品不處理付款或代替通路確認訂位。
10. 住宿與每日行程規劃不在本規格範圍，待 P1–P3 流程確認後另行設計。

## 3. 頁面需求

### P1｜草案與航班搜尋

- 出發地可用城市、機場名稱或 IATA 代碼搜尋。
- 目的地可搜尋、可多選，也能加入清單外的自訂地點。
- 去程與回程分別使用日期範圍；日期和地點未定案前不鎖定為單一選項。
- 旅客控制項分為成人和兒童。兒童人數變動時，逐位顯示年齡選項。
- 搜尋結果列出目的地、航空公司、去回程日期、航班號與供比較的單人示意票價。
- 「加入候選」是單一動作：建立候選並立即開始追蹤。加入後顯示已加入狀態；再次操作可移除候選並停止追蹤。
- 修改草案並重新搜尋時，必須清楚告知既有候選及追蹤會受到的影響；未來實作不得靜默清除使用者資料。

### P2｜候選比較與價格追蹤

- 顯示目前草案摘要：出發地、目的地選項、日期範圍及成人／兒童組成。
- 顯示候選清單；每筆可查看價格或移除候選。已停止追蹤的候選可恢復追蹤。
- 追蹤航班以頁籤切換，每個頁籤代表一組完整去回程組合。
- 每組顯示最新單人價格、歷史趨勢、觀察最低價和使用者目標價。
- 頁籤或卡片必須同時顯示兩段日期與航班號，避免把同一航班不同日期混為一筆。
- 使用者可選定一組航班並前往 P3；P3 使用此選擇及同一份 P1 旅客資料。
- 無候選、無追蹤資料、追蹤暫停及資料錯誤皆須有明確狀態與可理解的下一步。

### P3｜訂票通路與整組價格

- 頁面頂端摘要顯示已選目的地、去回程日期與航班、成人數、兒童數及每位兒童年齡。
- 對選定的完整來回組合查詢各訂票通路，不得把兩段單程票價相加冒充來回報價。
- 通路報價依整組旅客總價由低到高排序；最低總價需有文字標示，不只用顏色區別。
- 每筆報價至少呈現：
  - 通路名稱與通路類型（航空公司官網或訂票平台）
  - 整組旅客總價與幣別
  - 成人票價明細
  - 每位兒童的年齡與對應票價
  - 含稅狀態、行李與退改條件（通路有提供時）
  - 價格查詢時間、庫存或報價狀態
  - 前往該筆航班報價的通路連結
- 點擊通路連結後離開本產品，前往通路完成購買。使用者須被提醒最終價格與庫存以通路結帳頁為準。
- 若通路不支援指定兒童年齡、缺少任何旅客票價，或無法產生可用連結，須標示原因；不得把不完整報價排成可比較的整組總價。
- 查詢中、無結果、部分通路失敗、價格過期及服務錯誤均須有狀態、查詢時間及重試方式。

## 4. 旅客與報價資料契約

P1 至 P3 至少共用下列旅客資料：

```json
{
  "adults": 2,
  "children": [
    { "age_at_departure": 5 },
    { "age_at_departure": 7 }
  ]
}
```

正式 P3 報價結果應能關聯至通路與完整來回航班，並保存旅客票價明細、幣別、整組總價、稅費／行李／退改資訊、庫存狀態、報價時間與通路訂票連結。實際欄位、保存期限與 API 介面須在技術設計階段依所選通路確認。

不得以固定兒童折扣估算正式報價。若通路需要生日而不是出發日年齡，須先在技術設計中確認最少必要資料與隱私處理方式；本規格目前只要求年齡。

## 5. 原型與正式資料界線

目前原型只用固定示意航班與價格呈現互動。P3 原型依 P1 人數顯示成人及逐位兒童明細，並產生示意總價；目前兒童示意價格以成人票價八折呈現，這只是版面資料，不能作為實際票價或票規。訂票按鈕只顯示未串接提示，不會建立真實訂票連結。

正式版本必須使用通路回傳的旅客別票價、整組總價、條件與航班專屬連結，不得沿用原型折扣或假報價。

## 6. 技術背景與邊界

- 既有 `flight-tracker` 使用 Python 3.10+、FastAPI/Uvicorn、單頁 HTML 與 SQLite；啟動命令為 `cd flight-tracker` 後執行 `python src/main.py gui`。
- 現有原型位於 `scratch/`，不屬於正式應用程式入口，也沒有實際訂票通路查價。
- 既有航班技術規格與資料表描述 `passenger_count`，未定義成人數與逐位兒童年齡。正式整合前，須另行設計旅客組成及通路報價的 API／儲存介面；本規格不直接修改既有資料庫契約。
- P1 航班搜尋與 P2 價格追蹤須遵循既有航班 provider 設計：SerpApi＋Ignav、Ignav only 或 SerpApi only；hybrid 的實際路由依 provider 規格執行。這不等於 P3 訂票通路已確定；P3 的可訂價通路、報價 API 與 deep link 能力仍待核定。
- 前端延續現有 HTML/CSS/JavaScript 視覺語彙，支援淺色、深色與系統主題，並在窄螢幕下改為單欄呈現。
- 不在前端或規格範例中寫入 API 金鑰、帳密或個人付款資料。

### 專案結構與實作風格

- 原型：`scratch/ui-preview/trip-planner-v4.html`，僅供互動討論。
- 既有航班 GUI：`flight-tracker/web/`；API：`flight-tracker/src/api/`；航班資料與價格快照：`flight-tracker/src/db/`；測試：`flight-tracker/tests/`。
- P1–P3 是否整合至既有 GUI、另設旅程規劃頁或拆成獨立服務，須在技術計畫中確認；不得把忽略追蹤的 scratch 檔直接當正式頁面。
- Python 沿用既有 PEP 8 風格；前端延續單頁 HTML/CSS/JavaScript 模式。旅客組成與報價格式先以明確資料物件表示，例：`{ "adults": 2, "children": [{ "age_at_departure": 5 }] }`。不在呈現元件內散落票價計算或供應商轉換邏輯。

### 測試策略

- 單元測試：候選組合身分、成人／兒童旅客組成傳遞、完整總價計算、報價有效性與排序。
- API 契約測試：模擬各 provider 回應、兒童不支援、缺欄位、部分失敗、逾時與失效訂票連結；測試不得消耗真實查價額度。
- 瀏覽器驗收：完成 P1 搜尋與加入候選、P2 切換追蹤與選定航班、P3 檢視家庭總價並進入通路；涵蓋空狀態、錯誤狀態、窄螢幕及三種主題。
- 既有 Python 測試入口：`python -m unittest discover -s tests -v`（在 `flight-tracker/` 執行）。正式前端瀏覽器測試工具尚未指定，待技術計畫確認。

## 7. 驗收條件

| ID | 操作／情境 | 預期結果 |
| --- | --- | --- |
| P1-01 | 搜尋多個目的地與去回程日期範圍 | 結果符合草案範圍，列出完整去回程日期與航班號。 |
| P1-02 | 增減成人與兒童並設定兒童年齡 | 草案摘要保留正確人數與每位兒童年齡。 |
| P1-03 | 在航班結果加入候選 | 候選建立且價格追蹤同時啟動，不出現第二個「開始追蹤」要求。 |
| P1-04 | 移除候選 | 該候選與其追蹤同時移除；同航班號的不同日期候選不受影響。 |
| P2-01 | 切換兩組追蹤航班頁籤 | 各頁籤顯示正確日期、去回程班號、價格與走勢。 |
| P2-02 | 停止追蹤與恢復追蹤 | 停止後候選保留且不可混入追蹤統計；恢復後回到追蹤頁籤。 |
| P2-03 | 選定候選進入 P3 | P3 顯示同一組去回程航班，不要求重新選擇。 |
| P3-01 | 以成人與兒童混合旅客查價 | 查價請求包含成人數、每位兒童年齡；畫面顯示相同旅客組成。 |
| P3-02 | 比較多個通路有效報價 | 每筆顯示成人與逐位兒童票價、整組總價與通路條件，依總價排序。 |
| P3-03 | 通路缺少兒童報價或整組總價 | 顯示不完整原因，不以成人單價推算後混入有效報價排序。 |
| P3-04 | 點擊可用訂票連結 | 前往與顯示報價相符的通路航班頁；清楚提示結帳價格可能變動。 |
| P3-05 | 通路回報查無票、逾時或失敗 | 顯示對應狀態與最近查詢時間，允許重試，不把失敗當作無結果。 |
| UI-01 | 在窄螢幕及任一主題檢視 P1–P3 | 內容不溢出；人數、總價、最低價標記及操作維持可辨識。 |

## 8. 專案工作方式

- 原型檢視：開啟 `scratch/ui-preview/trip-planner-v4.html`。
- 既有航班 GUI：`cd flight-tracker`，再執行 `python src/main.py gui`。
- 既有航班單元測試：`cd flight-tracker`，再執行 `python -m unittest discover -s tests -v`。
- 實作風格：遵循既有單頁 HTML/CSS/JavaScript 與 Python/FastAPI 專案慣例；旅客組成與通路報價邏輯需集中處理，避免畫面元件各自計算票價。

## 9. 邊界

- **必須**：P1/P2/P3 共用同一份草案與旅客組成；以完整來回航班作比較；分辨示意價格和通路實價；顯示報價時間與通路條件。
- **需另行核定**：P3 查價供應商與可用訂票通路、年齡或生日資料需求、報價更新頻率、價格保存與提醒、成人／兒童最大人數限制、資料庫與 API 契約。
- **不得**：把單人追蹤價當作家庭總價；用固定折扣作正式兒童票價；把無法驗證的連結或無效報價當成可訂；未經使用者明確操作就靜默刪除候選或追蹤記錄；在原型或正式程式碼寫入秘密金鑰。
- **本階段不包含**：住宿、每日行程、付款與代訂。

## 10. 待決事項

1. P3 預計查詢哪些 OTA／航空公司通路，採用哪些已核定的 provider/API？
2. 各通路是否能以兒童出發日年齡查價；若要求生日，產品是否接受收集，如何最小化保存？
3. 目前原型允許最多 9 位同行者；正式產品是否需要人數上限，或依通路能力決定？
4. 一組航班有多個可用通路報價時，是否提供「僅看含託運行李」或其他條件篩選？
